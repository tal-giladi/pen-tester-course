# A6 — Pivoting & segmented networks · instructor material & grading key

> Instructor material. Not linked from `_sidebar.md`. Do not distribute to students. The topology
> and route below are the ones shipped in `labs/lab-12-pivot/` (see its `README.md` and
> `verify.py`); reconcile against the compose file if the lab changes.

## What this assessment tests

Turning a foothold host into a routing vantage point (M12), discovering topology by enumeration
rather than assumption, and articulating *segmentation* as a control failure with a network-level
fix (M11 feeds the credential reuse if a hop needs it).

## Topology (ground truth)

```text
  ws ──net_edge── dmz ──net_internal── internal ──net_restricted── restricted (/flag)
 (you)          pivot#1               pivot#2                     (unreachable from ws)
```

- `ws` (attacker) sees `net_edge` only → can reach `dmz`, cannot reach `internal` or `restricted`.
- `dmz` is **dual-homed** on `net_edge` + `net_internal` → bridges to `internal`.
- `internal` is **dual-homed** on `net_internal` + `net_restricted` → bridges to `restricted`.
- `restricted` hosts `http://restricted/flag` (the `LAB-FLAG-{uuid}` marker) and has no route back
  to `ws`. **Two pivots** are required, not one.

## Intended route(s)

Student has `ssh lab@dmz` from `ws` (throwaway key at `~/.ssh/id_ed25519`). Discovery first:
`ip -4 addr` / `ip route` on `dmz` reveals `net_internal` and the `internal` host; repeat on
`internal` to reveal `net_restricted` and `restricted`.

### Route A — SSH ProxyJump chain (simplest to verify)

```bash
ssh -J lab@dmz lab@internal 'curl -s http://restricted/flag'
```

One line proves the whole chain: jump through `dmz` to `internal`, and from `internal` (which is on
`net_restricted`) fetch the flag. This is the fastest acceptance proof.

### Route B — Dynamic SOCKS + proxychains (the general technique, carries any tool)

```bash
# hop 1: SOCKS proxy through the DMZ
ssh -D 1080 -N lab@dmz
# hop 2: extend to net_restricted via internal — e.g. a forward through internal, or a second
#        SSH dynamic proxy chained from internal, then point proxychains at it:
proxychains4 curl -s http://restricted/flag
proxychains4 nmap -sT -Pn restricted        # tool traffic crossing the pivot (distinction)
```

Acceptable variants: nested `-D` proxies, local/remote forwards (`ssh -L`/`-R`) staged across the
two hops, or a reverse tunnel (Chisel) if the student prefers — any route that (a) is reproducible
and (b) reaches the flag through the pivots. `verify.py` confirms the chain is *possible*; it is not
the student's solution.

## Expected evidence

- **"Before":** `curl --max-time 4 http://restricted/flag` from `ws` **fails** (no route) — the
  baseline that makes the pivot meaningful.
- **"After":** the flag (`LAB-FLAG-{uuid}`) read *through* the chain, with the command shown.
- The **topology map** built from per-hop `ip addr`/`ip route`/reachability output.
- Tunnels **torn down** at closeout (no lingering `-D 1080`).

## Common wrong turns

- **Assuming one pivot.** Reaching `internal` and trying to hit `restricted` from `ws` — misses the
  second dual-homed hop. The route is `ws → dmz → internal → restricted`.
- **Reading the topology from the README** instead of discovering it — fails the discovery band.
- **Trying to reach `restricted` directly** from `ws` repeatedly (it has no route) rather than
  enumerating interfaces on the foothold.
- **proxychains misconfig** — wrong `socks` line/port, or forgetting `-Pn`/TCP-connect scans through
  a SOCKS proxy (SOCKS can't carry raw SYN scans; use `-sT`).
- **Leaving tunnels up** — OPSEC/professionalism deduction; correct closeout tears them down.
- **Impact = "an attacker can pivot"** — not a business impact; must be "a single DMZ compromise
  reaches the crown-jewel data, so the perimeter is the only real control."

## Grading key

Suggested weighting (100):

- **Flag via pivot + before/after (35):** reproducible chain reaches the flag; baseline failure
  shown.
- **Discovery (25):** topology map built from own enumeration; both dual-homed hosts and the
  two-pivot route correctly identified.
- **Segmentation finding (20):** rubric-complete; correctly frames the *missing control between
  segments* (not the dual-homed host per se) as root cause; business-terms impact; specific
  network-level remediation (deny-by-default ACL/firewall between `net_internal` and
  `net_restricted`, host-based firewalling on the dual-homed hosts, no transitive routing) with a
  verification step.
- **Professionalism (10):** isolation verified; tunnels torn down; deterministic evidence naming.
- **Distinction (+10):** demonstrated *both* Route A and Route B with tool traffic (e.g. an
  `nmap`/`curl` scan) crossing the pivot, plus detection reasoning (what a NIDS/flow log would show
  on `net_internal`).

**Fail conditions:** flag not reached through the pivot; topology assumed; no marker evidence;
persistent tunnels or out-of-scope hosts touched; isolation not verified.

## Model check-yourself answers (abbreviated)

1. It proves `restricted` is reachable *from `internal`* (they share `net_restricted`) but not from
   `ws`; and it disproves "segmentation protects it" — a compromised `internal` (via `dmz`) bridges
   straight in.
2. `-J` for a quick, credentialled reach and single commands; `-D`+proxychains when you need to run
   arbitrary tooling (e.g. `nmap`) across the pivot. Only the SOCKS route carries `nmap`.
3. The missing control is the vulnerability; the dual-homed host is normal architecture. Remediation
   must be the enforced boundary (deny-by-default between segments), not "remove the second NIC,"
   which usually isn't feasible.
4. "Can pivot" is a capability; the business impact is *what it reaches* — the crown-jewel data — and
   the consequence (breach of that data from a single perimeter foothold).
5. Leftover `-D 1080` is an open backdoor into the client network (OPSEC/liability) and unprofessional
   closeout; correct action is to tear down all forwards and confirm none persist.
