# Instructor / solutions — Assessment 4 (Web &amp; API penetration test)

> Instructor material. Not linked from `_sidebar.md`. Have students complete the assessment before
> reading. All work targets the isolated `lab-07-web` (`web:5000`) and `lab-08-api` (`api:5000`)
> services, with synthetic users and benign `LAB-FLAG-*` markers, on no-egress networks. Never a
> real system.

## What this assesses

M07 + M08 as a full engagement: from a low-privilege customer position, map the surface, test
systematically across the OWASP Web/API Top 10, prove ≥3 significant findings (≥1 web-only, ≥1
API-only), chain where it raises impact, and report each to the template with justified severity.
The most advanced, least-scaffolded assessment: the student designs everything.

## The labs' surfaces (from the lab READMEs)

**Web (`lab-07-web`):**

| Endpoint | Class |
|---|---|
| `/search?q=` | SQL injection **and** reflected XSS |
| `/api/orders/<id>` | IDOR / BOLA (no ownership check) |
| `/login` | weak JWT (weak HMAC secret; `alg:none` accepted); cookie missing flags |
| `/api/admin/users` | BFLA (trusts client `role` claim) |

| `/ping?host=` | OS command injection |
| `/download?file=` | path traversal |
| `/render?name=` | SSTI |
| `/upload` | unrestricted file upload |

Internal-only (reachable **only** via SSRF): `http://internal-api/secret`,
`http://metadata/latest/meta-data/...`.

**API (`lab-08-api`):**

| Endpoint | Flaw | OWASP API |
|---|---|---|
| `POST /api/v1/login` | weak JWT (weak HMAC secret) | API2 |

## Intended findings and the chains worth showing

A strong submission maps the surface (auth model = JWT bearer / cookie), then proves a spread. The
highest-value items:

**1. Weak/`alg:none` JWT → authentication bypass / account takeover (the key chain).** The token
is signed with a weak HMAC secret and the server also accepts `alg:none`. The student forges a
token for another user (or elevates the `role` claim). Show the chain: this turns every BOLA read
into a full **account takeover / privilege escalation** — the single most severe finding. CWE-347
(improper signature verification) / OWASP API2. Fix: verify the signature with a strong secret,
pin the algorithm server-side (reject `none`), validate claims server-side.

**2. BOLA / IDOR on `/api/v1/users/<id>` and `/api/orders/<id>`.** Change the id, retrieve another
principal's object — proven with the `LAB-FLAG-*`/cross-account data. Compounded by **excessive
data exposure** (the user object returns `ssn` and `password_hash` — a finding *on its own*, API3,
even before any bypass). CWE-639 / OWASP API1 + API3. Fix: server-side ownership check per object;
return only necessary fields (DTO/allowlist).

**3. BFLA on `/api/admin/users` and `/api/v1/admin/flag`.** The server checks that a claim *exists*
rather than that it *equals admin*, so a non-admin token reaches admin function. CWE-285 / OWASP
API5. Fix: enforce role server-side against a trusted source, not a client-controlled claim.

**4. Mass assignment on `POST /api/v1/users`.** Client sets `role` and the server honors it —
instant privilege escalation at creation. CWE-915 / OWASP API3. Fix: bind only allowlisted input
fields; never let the client set authority fields.

**5. Improper inventory: `/api/v2/users/<id>` forgot auth entirely (API9).** An unauthenticated
read — often the fastest win. Fix: decommission/authenticate old versions; inventory all versions.

**6. SSRF on `/fetch?url=` (API-adjacent / web).** Point it at `http://internal-api/secret` or the
metadata simulation to retrieve the internal-only marker. The no-egress network is **not** a
mitigation of the bug — it only bounds the blast radius in the lab; the vulnerability is the
server fetching an attacker-controlled URL. CWE-918. Fix: allowlist destinations, block internal
ranges/metadata, no raw user URL to the fetcher.

**7. GraphQL: introspection on + unauthorized `adminSecret`/`allUsers`.** Use introspection to map
the schema, then read fields lacking authz. OWASP API1/API5/API8. Fix: disable introspection in
prod; enforce field-level authorization.

**8. The injection family (web):** SQLi and reflected XSS on `/search`, OS command injection on
`/ping`, SSTI on `/render`, path traversal on `/download`, stored XSS on `/profile`, unrestricted
upload on `/upload`. Each proven by its observable result / marker. Roots: unparameterized query,
unescaped output, shell concatenation, template eval of input, unsanitized path, no upload
validation.

**≥3 findings, ≥1 web + ≥1 API required.** A model set: JWT-bypass chain (API) + BOLA/excessive
data (API) + SQLi or SSRF (web). The JWT→BOLA chain and the SSRF-to-internal-secret are the two
"chain" demonstrations that earn the exploitation-and-chaining points.

## Common wrong turns

- A long list of unproven "potential" issues instead of ≥3 proven, well-explained findings (depth
  beats breadth here).
- Treating excessive data exposure as merely part of BOLA — it is a separate finding (API3).
- Calling the SSRF a non-issue "because no Internet" — the no-egress design bounds blast radius,
  not the bug; still a serious finding proven via the internal marker.
- Assuming admin instead of *demonstrating* the path from the low-priv customer position.
- CVSS that reflects assumed rather than demonstrated impact, with no noted ceiling.
- "Add a WAF" remediation instead of root-cause (parameterize, verify the signature, server-side
  authorization, allowlist, escape on output).
- Destroying state (wiping data, mass-uploading) rather than minimal proof.

## Expected evidence / markers

Exact request/response per finding; the `LAB-FLAG-*` marker, cross-account data, or internal-only
response as proof; the forged token and the server accepting it for the JWT chain; the SSRF
response body from `internal-api`/metadata. `verify.py` per lab is a health check, not a solution.

## Grading key (100 pts)

| Dimension | Pts | Award full when… | Deduct when… |
|---|---|---|---|
| Method &amp; coverage | 20 | systematic plan mapped to OWASP Web/API Top 10; auth model understood; surface enumerated incl. discovery aids; prioritization argued | ad-hoc pokes; no coverage story; ignored the openapi/introspection aids |
| Evidence | 15 | every finding reproducible without them; exact req/resp + marker | asserted, not shown |
| Exploitation &amp; chaining | 25 | findings proven; mechanisms correct; ≥1 impact-raising chain demonstrated + explained (JWT→BOLA or SSRF→secret) | no chain; "likely vulnerable" without PoC |
| Impact &amp; severity | 15 | business impact tied to client assets; CVSS justified per metric; demonstrated not assumed; ceiling noted | generic severity; unjustified scores |
| Remediation | 15 | root-cause, layered, verifiable per finding | "add a WAF"; class name only |
| Reporting | 10 | ≥3 findings, ≥1 web + ≥1 API, template fully filled, prioritized, client-ready | <3 findings; wrong spread; missing fields |

Example CVSS anchors: JWT-bypass/ATO `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N` ≈ 9.1
(Critical); BOLA read `AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N` ≈ 6.5; SSRF-to-secret High. Accept a
defended score reflecting what was demonstrated.
